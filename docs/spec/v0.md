# acceleread v0 specification

acceleread is a Python library that turns PDFs and HTML into structured **Document Records**. It classifies them against a user-defined **Taxonomy** and answers user-defined **Questions** through a pluggable **Classifier** (Jev by default). A CLI, an async HTTP API and a small web UI sit on top of the library.

This document is the hand-off for building v0. Each decision was made in a ticket on the [v0 map](https://github.com/Jarrod-Bob/acceleread/issues/1), and the ticket holds the reasoning and evidence. This spec states *what* to build and links to *why*. Where a later ticket amended an earlier one, this spec follows the later decision. Section 15 lists every such reconciliation.

- **Glossary:** [`CONTEXT.md`](../../CONTEXT.md). Capitalised terms (Document, Page, Section, Job, Judgment, Workspace, …) are used as defined there.
- **ADRs:** [`docs/adr/`](../adr/), 0001–0010.
- **Dogfood corpus:** [`corpus/`](../../corpus/). 60 labelled EDGAR filings plus derived PDFs.

## 1. Scope

**In v0**
- Inputs: PDF and HTML Documents, from local paths, uploads or URLs ([API and CLI surface](https://github.com/Jarrod-Bob/acceleread/issues/9)).
- Local Extraction: the PDF text layer, with per-Page OCR when needed. Section detection for filings.
- Judgments through the Classifier seam: at most one flat Taxonomy plus any number of Questions per Job.
- Escalation of low-confidence Judgments: flagged always, and optionally sent to an LLM.
- Batch Jobs of 10k–100k Documents on one machine. Library, CLI, HTTP API and web UI.
- An evaluation harness.

**Out of scope** (from the map's Out of scope section)
- Hierarchical Taxonomies.
- Image inputs and formats other than PDF and HTML.
- The financial-health verdict itself, which is a separate example app on the API.
- Distributed or multi-machine workers.
- Self-hosted or fine-tuned classification models.
- Multi-tenant SaaS, users and accounts.
- Cloud OCR.
- GPU builds.
- Following incorporation-by-reference pointers into other Documents.
- Fetching from sources such as EDGAR, beyond a downloader in `examples/`.
- A Prometheus `/metrics` endpoint.
- An in-browser Question Set editor.

**Privacy boundary** ([ADR 0004](../adr/0004-local-extraction-cloud-classification.md)): Extraction always runs locally and never needs the network. Text leaves the machine only when sent to a cloud Classifier (Jev, or Claude for Escalation). Jev's zero data retention is enterprise-only, and this is documented for users.

## 2. Repository and packaging

Source: [How is acceleread packaged and distributed?](https://github.com/Jarrod-Bob/acceleread/issues/24), [Is acceleread MIT or Apache-2.0?](https://github.com/Jarrod-Bob/acceleread/issues/20), [ADR 0003](../adr/0003-permissive-dependencies-only.md), [ADR 0005](../adr/0005-torch-free-core-quality-extra.md).

**Repository layout.** This repo is a uv workspace monorepo with one lockfile:
- `packages/acceleread`: the library.
- `packages/acceleread-eval`: the evaluation harness, not shipped to users.
- `examples/financial-health` and other consumers, which depend on the library by path.

**Distribution.**
- v0 is distributed by path, or by git tag (`…@v0.1.0#subdirectory=packages/acceleread`).
- PyPI publishing comes later, through Trusted Publishing from GitHub Actions.
- Versions follow SemVer from `0.1.0`. A **major** bump means the storage format or the Record `schema_version` changed.

**Pip package and extras.**

| Package | Contents |
|---|---|
| `acceleread` (core, torch-free) | pydantic v2, pypdfium2, `tesserocr` (wheels bundle libtesseract 5.5), lxml, FastAPI with uvicorn and Jinja2, `typesafe-sdk[http2]`, httpx, psutil. Vendors `eng.traineddata` (tessdata_fast), htmx and CSS |
| `[quality]` | `docling-slim[convert-core,format-pdf,feat-ocr-rapidocr-onnx,models-local]` on CPU torch, using the documented PyTorch CPU index. Never the `models-onnxruntime` extra |
| `[llm]` | `anthropic` |
| `[edgar]` | `edgartools`, pinned exactly |
| `[all]` | everything above |

**Platforms.** Python 3.12–3.14 on Linux x86_64/aarch64 and macOS. Windows runs through WSL or Docker only.

**Docker images.** On GHCR, multi-arch (amd64 and arm64), `python:3.12-slim` base, CPU only. Both run `acceleread serve` with the Workspace at `/data`.
- `acceleread:<v>`: core + `[llm]` + `[edgar]` + tessdata `eng deu fra spa ita por nld`. Target ≤ 500 MB.
- `acceleread:<v>-quality`: adds `[quality]` with the Docling and PP-OCR (`latin`) weights baked in at build time. Target ≤ 2 GB.

**Model weights for pip installs.** `acceleread models fetch` downloads pinned revisions, with recorded hashes, into the Workspace's `models/`. With `ACCELEREAD_OFFLINE=1`, any runtime download is an error. `acceleread doctor` reports Tesseract, language packs, models and extras.

**Licensing.**
- acceleread is Apache-2.0, `Copyright 2026 The acceleread Authors`. Source files carry SPDX headers. There is no DCO or CLA. `LICENSE`, `NOTICE` and `AUTHORS` are needed because the repo is public.
- Dependencies must be permissive (ADR 0003). CI checks every extra's resolved environment, and the images, against an allowlist: MIT, BSD-2/3, 0BSD, ISC, PSF, Apache-2.0, MPL-2.0 and CDLA-Permissive.
- Model weights and vendored assets are listed in `THIRD_PARTY_NOTICES.md`.
- Never depend on PyMuPDF, Ghostscript or OCRmyPDF, or Marker/Surya weights.
- SEC filings are never committed or shipped.

**Upstream:** file the two torch-free Docling fixes upstream (goodwill, off the critical path).

## 3. Domain model

The terms are defined in [`CONTEXT.md`](../../CONTEXT.md):

| Area | Terms |
|---|---|
| Ingestion | Document, Page, Section, Extraction, Extraction Profile, Section Verification, Document Record, Coverage, Job, Workspace |
| Judgments | Taxonomy, Category, Classifier, Judgment, Classification, Question, Question Set, Answer, Escalation, Review |

Key relationships:
- **A Document is one source file** ([ADR 0001](../adr/0001-one-file-per-document-offset-addressed-text.md)). An EDGAR exhibit is its own Document, joined to its filing by `source.group` (the accession number).
- **Every Document yields exactly one Record**, even on failure.
- **A Job** judges each Document against at most one Taxonomy and any number of Questions, with at least one of either.
- **Every Judgment** (a Classification, an Answer, or one of acceleread's own checks) is a single Noul, Score or Choice put to a Classifier. Each one records its own Coverage.

## 4. Extraction

Sources: [Which PDF extraction and OCR engine should v0 use?](https://github.com/Jarrod-Bob/acceleread/issues/2), [Should Jobs default to quality or fast extraction?](https://github.com/Jarrod-Bob/acceleread/issues/11), [When should the fast extraction path send a Page to OCR?](https://github.com/Jarrod-Bob/acceleread/issues/12), [How does v0 choose the OCR language?](https://github.com/Jarrod-Bob/acceleread/issues/21), [ADR 0004](../adr/0004-local-extraction-cloud-classification.md), [ADR 0005](../adr/0005-torch-free-core-quality-extra.md).

### 4.1 Extraction Profiles (PDF only)
- **`fast` (default):** the pypdfium2 text layer, plus Tesseract 5 (via `tesserocr`) on Pages the OCR rule flags.
- **`quality` (opt-in, `[quality]`):** Docling with RapidOCR on ONNX Runtime, pinned and not set to `auto`. Docling's OCR is limited to the Pages the shared OCR rule flags. Tables are off by default (`tables: true` turns them on).
- The Profile is set per Job, with a per-Document override. Automatic upgrade to `quality` is deferred until the evaluation harness shows when it pays.
- **HTML ignores the Profile.** EDGAR HTML gets Sections from edgartools when `[edgar]` is installed, and from the Item regex otherwise. Other HTML gets plain extraction.

### 4.2 The OCR rule, shared by both Profiles
The rule is evaluated per Page from pypdfium2 signals, without rendering. The first match wins:
1. **Fewer than 80 non-space characters:**
   - the union of image boxes covers ≥ 60% of the Page → **OCR**
   - else ≥ 20 vector path objects → **OCR**
   - else → **keep**
2. **≥ 5% bad characters** (control, private-use, unassigned, U+FFFD) → **OCR**.
3. **Fewer than 70% of words found in a dictionary** → ask the Classifier one Noul on the first 2,000 characters: *"Are most of the words in `page_text` correctly spelled real words in some human language?"* At ≥ 0.6, **keep**; otherwise **OCR**.
   - Runs only when a judgment-capable Classifier is configured; otherwise the Page goes to OCR and the Record notes the check was skipped.
   - Runs only when every OCR language configured for the Document has a bundled wordlist (English only in v0); otherwise step 3 is skipped.
4. Otherwise **keep** the text layer.

Further rules:
- Existing OCR layers are judged by this same rule.
- Text beside a large image is kept in `fast`.
- Per-Page image coverage is recorded.
- All thresholds are starting values for the evaluation harness to tune.

### 4.3 OCR language
- `ocr_languages` is set per Job (ISO 639-1, default `["en"]`, several allowed), with a per-Document override. `auto` is reserved but not implemented.
- Codes map to Tesseract (`eng`, `deu`) and RapidOCR model families.
- `jobs:validate` fails when the Profile can't serve a language or a language pack is missing.
- `acceleread ocr add-language xx [--from-file]` installs `tessdata_fast` packs into the Workspace's `models/tessdata/`.
- v0 has no translation step.

### 4.4 Sections
Sources: [How reliably can filing sections be detected in EDGAR HTML and PDF reports?](https://github.com/Jarrod-Bob/acceleread/issues/14), [What are the canonical Section keys and how does each form map onto them?](https://github.com/Jarrod-Bob/acceleread/issues/22).

**`SectionDetector` seam.** A detector returns Sections. Each has `key`, `label`, `form_ref`, `spans` (character offsets), `method`, `confidence`, `flags` and `est_tokens`. A Section is one contiguous span. A key may have several Sections, and a Section may carry several keys (e.g. "Items 1 and 2").

**Detectors, by input:**
- **EDGAR HTML:** edgartools (`[edgar]`), otherwise the Item regex.
- **PDFs:** in `fast`, Item regex candidates. In `quality`, Docling `section_header` items plus the Item regex.
- **Annual reports with no Item numbers:**
  1. Candidates come from top-level headings and the PDF outline.
  2. Candidates are matched against a synonym list.
  3. Headings left unmatched get **one Jev Choice per Document** over the 10 keys plus `none` (method `heading_classified`). This step is skipped without a judgment-capable Classifier.

**Canonical keys.** A closed set of 10. A detector may declare extra keys. Everything else is `other` and can't be read.

| key | 10-K | 10-Q | 20-F | Annual report synonyms |
|---|---|---|---|---|
| `business` | 1 | — | 4 | Strategic report, Business overview, Our business |
| `risk_factors` | 1A | II.1A | 3.D | Principal risks (and uncertainties), Risk factors |
| `cybersecurity` | 1C | — | 16K | Cybersecurity |
| `legal_proceedings` | 3 | II.1 | 8.A.7 | Legal proceedings, Litigation |
| `mdna` | 7 | I.2 | 5 | Operating and financial review, Financial review, Management's discussion |
| `market_risk` | 7A | I.3 | 11 | Market risk, Financial risk management |
| `financial_statements` | 8 | I.1 | 17 / 18 | Financial statements, Consolidated financial statements |
| `controls` | 9A | I.4 | 15 | Internal control(s), Controls and procedures |
| `governance` | 10–14 | — | 6 | Directors' report, Corporate governance, Remuneration report |
| `exhibits` | 15 | II.6 | 19 | — |

8-K has no canonical keys. Its Items are detected as `other`, with `form_ref` such as `8-K 2.02`, and Questions over 8-Ks read the whole Document.

**Section Verification** runs only for keys that some Question in the Job `reads`, and only when a judgment-capable Classifier is configured.
- Candidates found by regex or Docling headings go through one request per Document with one Choice per key read: "which candidate starts this Section?", with a `none` option.
- edgartools Sections get a Noul: "real content, or a pointer or cross-reference index?"
- It's skipped for TOC-anchor Sections with confidence ≥ 0.9, and always run for regex-only and `heading_classified` Sections.
- A Section that fails Verification, or has low confidence, doesn't exist for `reads`.
- Verification never escalates.

**Pointers.** A Section that is only a pointer (e.g. "see Exhibit 13") is flagged `pointer` and counts as missing. Coverage records `pointer → Exhibit 13`.

## 5. Judgments: Taxonomy, Questions and the planner

Sources: [How are Questions defined and attached to a Job?](https://github.com/Jarrod-Bob/acceleread/issues/15), [What does the Classifier seam look like, and when does it escalate?](https://github.com/Jarrod-Bob/acceleread/issues/8), [How should documents longer than Jev's 32k-token state limit be classified?](https://github.com/Jarrod-Bob/acceleread/issues/3), [What does Jev integration cost and look like per document?](https://github.com/Jarrod-Bob/acceleread/issues/4), [ADR 0006](../adr/0006-one-classifier-request-per-section-group.md), [ADR 0007](../adr/0007-thin-classifier-seam-shared-planner.md).

### 5.1 Definitions
- **Taxonomy:** flat, with named and described Categories. `other` is added automatically unless the user defines one. More than 255 options (or the Classifier's declared maximum) is an error, and Taxonomy text over 20% of the budget is a warning. The Taxonomy may declare `reads`. It **never skips**: when its Sections are missing, it falls back to head+tail.
- **Question:**
  - `name` (unique across the Job).
  - `kind`: `noul`, `score` (ordered criteria from low to high) or `choice` (named options with descriptions). Choice gets the Taxonomy's checks except the automatic `other`.
  - `instructions`, plus `criteria` for Score and Choice.
  - Optional `reads` (canonical keys), `fallback: head_tail`, and `escalate_below`.
- **A missing Section** skips the Question: the Answer is `null` with a reason, and Coverage shows nothing was read. The Question reads head+tail instead only if it sets `fallback: head_tail`.
- **Question Set:** a named, versioned YAML or JSON file of Questions plus an optional Taxonomy. A Job references Sets by path (inlined over HTTP) and can add inline Questions. A name clash across everything the Job pulls in is an error. There is no registry. `examples/financial-health` ships a Set.

### 5.2 State sent to the Classifier
- The state is always `{"document": {title, company, form, period, sections: {key: text}}}`, with `text` in place of `sections` for a whole-Document read.
- Instructions refer to `document`, and submit warns when an instruction never does.

### 5.3 Planner (above the seam)
- **Grouping:** one request per distinct `reads` set per Document (ADR 0006). The Taxonomy joins its group.
- **Budget,** from the Classifier's `capabilities`. For Jev:
  - The limit is 32k tokens for state plus the longest Judgment. Tokens are estimated as **characters ÷ 3.0**, plus the tokens of each Judgment's instructions and criteria.
  - A Document or group that fits is sent whole. One that doesn't is cut **head+tail**, on Page boundaries where possible, at about 25% head and 75% tail. A group's Sections are cut in proportion.
  - On a 400 `max_tokens_exceeded`, the state is shrunk by 15% and retried once.
  - Coverage records any truncation or shrink.
- **Judgment cache:** Workspace-wide ([ADR 0010](../adr/0010-per-job-directories-shared-judgment-cache.md)), keyed by hash(state, Judgment definition, model version). `--no-cache` bypasses it.
- Chunk-and-aggregate is deferred to an evaluation variant.

### 5.4 Classifier seam
- The seam is `judge(state, judgments: {name → Noul|Score|Choice}) → {name → result}`, plus `capabilities` (kinds supported, max Choice options, token budget, characters-per-token estimate). Extraction's own Judgments use the same call, and get "unsupported" when the Classifier can't answer them.
- **Jev** (default): the async `typesafe-sdk` with HTTP/2, pinned to `jev-1.13.0`. Its costs are $0.042 per 1M input tokens, with output free.
- **LLM** (`[llm]`): Claude through the same seam. The default is `claude-opus-5-5` at low effort, sent with the server-side refusal `fallbacks` parameter.

### 5.5 Escalation
- **Trigger:** `escalate_below` per Taxonomy or Question, compared with confidence. There is **no default**. Below the threshold, a Judgment is always **flagged**.
- **Automatic LLM escalation** is opt-in per Job. The planner re-plans against the LLM's `capabilities`, so the LLM reads untruncated Sections. Judgments of one Document that share `reads` go in one structured-output call.
- **Cap:** `escalation_max` per Job, default 2% of Documents. Past the cap, Judgments are only flagged.
- The escalated result becomes the Judgment of record, with `probabilities` and `confidence` set to `null`. The first-pass result is kept under `escalation.first`.
- acceleread's own checks never escalate.

## 6. Document Record

Sources: [What is the Document Record schema?](https://github.com/Jarrod-Bob/acceleread/issues/7) as amended by tickets 8, 9, 18, 21 and 23, [ADR 0001](../adr/0001-one-file-per-document-offset-addressed-text.md).

- Pydantic v2 models are the source of truth, and a JSON Schema is generated from them.
- One JSON object per Record. A Job exports JSONL with exactly one line per input Document, plus the Job manifest beside it.
- Text is inline unless `include_text=false`. Offsets stay valid either way.
- Metadata comes from code only, each field as `{value, source}`.

```
DocumentRecord
  schema_version, record_id, job_id, external_id?, user_metadata{}
  status: ok | partial | failed | cancelled          errors[]: {stage, code, message, page?}
  attempts
  source: {filename, format: pdf|html, sha256, bytes, group?: accession}
  metadata: {title, date, company, cik, form, period, …  each {value, source}}
  extraction_profile: fast | quality
  text?                                               # omitted with include_text=false
  pages[] (PDF only): {number, start, end,
                       method: text-layer | ocr-full | ocr-regions,
                       engine, engine_version, ocr_languages[], ocr_confidence?,
                       ocr_decision: {step, reason, chars, word_ratio, bad_char_ratio,
                                      image_coverage, path_count, jev_real_words?, jev_skipped},
                       image_coverage}
  sections[]: {keys[], label, form_ref, spans[{start,end}], method, confidence,
               verification: {status, p}, flags[] (incl. pointer), est_tokens}
  taxonomy: {name, hash}?
  classification?: Judgment
  answers{name → Judgment | {value: null, skipped: reason, coverage}}
  usage:   {requests, input_tokens, output_tokens, ocr_pages, cache_hits}
  timings: {queued_ms, extract_ms, ocr_ms, classify_ms, escalate_ms}

Judgment   := {kind, value, probabilities?, confidence?, classifier{id, model, version},
               coverage, escalation}
Coverage   := {sections[] | page_ranges[], truncated, shrunk, est_tokens, input_tokens, note?}
escalation := {status: none | flagged | escalated | failed, reason?,
               first?: {classifier, value, probabilities, confidence, coverage}}
```

For a Classification, `value` is the Category. Escalated Judgments have `probabilities: null` and `confidence: null`. `status: cancelled` marks Documents left unprocessed by a cancel; resume re-queues them.

## 7. Jobs and the runner

Sources: [ADR 0002](../adr/0002-in-library-job-runner-no-broker.md) (amended), [ADR 0008](../adr/0008-one-running-job-per-machine.md), [How many OCR workers run, and how does the pool recover from crashes?](https://github.com/Jarrod-Bob/acceleread/issues/18), [How does the runner budget the Classifier's rate limit?](https://github.com/Jarrod-Bob/acceleread/issues/19), [What API and CLI surface does v0 expose?](https://github.com/Jarrod-Bob/acceleread/issues/9).

### 7.1 Job spec and manifest
- One Pydantic **Job spec** is used everywhere: Python `acceleread.run(spec)` (an async iterator of Records), `POST /v1/jobs`, and the CLI's `job.yaml` plus flags.
- **Fields:** inputs, Taxonomy, Question Set references, inline Questions, `extraction_profile` (with per-Document override), `ocr_languages`, `escalate_below`, LLM escalation (on/off, model, `escalation_max`), `max_cost_usd`, cache on/off, and the source User-Agent.
- **The manifest** is the resolved spec: Sets inlined with name, version and hash, defaults filled in, plus the price-table version. It's written before the first Record.
- **The manifest is immutable once the Job starts, except `max_cost_usd`.** Any other change means a new Job, and the Judgment cache makes unchanged Judgments free.

### 7.2 Scheduling
- **One running Job per Workspace runner, FIFO.** Single-Document ingests jump the queue: they interleave between the running Job's Documents, and get priority in the rate limiter.
- **Runner lease:** held in `catalog.sqlite`, with a heartbeat. The holder is the single SQLite writer. `acceleread run` while `serve` holds the lease joins the shared FIFO and streams its Records.

### 7.3 Pipeline and Document states
- **Pipeline:** queued → extracting → `extracted` (persisted at once, with Pages, Sections and compressed text) → classifying → done or failed. A cancel ends with `cancelled`.
- **Backpressure:** new extraction stops while more than 500 Documents are waiting for the Classifier. Only IDs are held in memory.
- **Resume** re-queues `cancelled` and unstarted Documents, and never redoes OCR for an `extracted` Document.
- **Retry:** `retry --failed` re-queues failed Documents under the same manifest and replaces their Records.

### 7.4 Extraction workers
- **Our own worker manager** over `multiprocessing` (spawn), not `ProcessPoolExecutor`, so a single worker can be killed.
- **One task is one Document.** OCR engines are pinned to one thread.
- **Workers are generic,** lazy-loading Tesseract or Docling as needed. Each is recycled after 200 Documents.
- **Default counts:** `fast` uses physical cores − 1, `quality` uses cores ÷ 4 (4 torch threads each). Both are capped by RAM ÷ a per-Profile estimate. `--ocr-workers` and `--threads-per-worker` override them.
- **Limits:**
  - Timeout: `60 s + 20 s × Pages needing OCR` for `fast`, `60 s + 6 s × Pages` for `quality`, capped at 30 min.
  - Memory per worker: 2 GB for `fast`, 6 GB for `quality`. Watched with psutil.
- **Failures:**
  - A crash or memory kill gets one retry in a fresh worker, then `failed`.
  - A timeout fails immediately.
  - Crash failures reaching 5% of finished Documents auto-cancel the Job with reason `crash_rate`.

### 7.5 Classifier rate limiting
- **One limiter per Classifier per runner:** a dual token bucket (tokens/s charged by estimate and reconciled with `usage`, plus requests/s) and at most 64 requests in flight.
- **Ceiling:** 80% of published limits (Jev: 80K tok/s, 64 req/s), overridable with `classifier.rate_limit`.
- **AIMD:** on a 429 or 529, the rate drops to 70% and `retry-after` is honoured. After 60 s with no 429, it rises by 5% of the ceiling.
- The Claude limiter reads Anthropic's rate-limit headers.
- **Failure policy:**
  - 429, 529, timeouts and connection errors never fail a Document; the request is re-queued.
  - Persistent 5xx (5 tries) → `failed: classifier unavailable`.
  - A 400 after the shrink → `failed: over budget`.
  - A 422 → the Job is auto-cancelled with reason `classifier_rejected`.
  - No success for 15 minutes → the Job shows `stalled`, and keeps waiting.
- `jobs:validate` estimates the Classifier-bound duration. No enterprise limit is needed for v0.

### 7.6 Single-Document ingest
`POST /v1/documents:ingest` runs a Job of one, with `kind: ingest`:
- Limits: 20 MB, 10 Pages needing OCR, 120 s.
- Escalation is allowed.
- Ingest Jobs are hidden from Job lists by default.

## 8. Storage: the Workspace

Source: [Where do Jobs, Records, uploads and Reviews live, and how long are they kept?](https://github.com/Jarrod-Bob/acceleread/issues/17), [ADR 0010](../adr/0010-per-job-directories-shared-judgment-cache.md).

```
$ACCELEREAD_HOME (default ~/.acceleread, --workspace to override)
  catalog.sqlite      Job list, FIFO order, runner lease
  cache.sqlite        Judgment cache (versioned format)
  models/             tessdata, Docling/PP-OCR weights
  jobs/<id>/
    job.sqlite        Document state and queue, Records, Review log
    manifest.json
    summary.json      frozen at Job end
    job.log           JSON lines
    inputs/           uploads and fetched URLs, named by content hash
```

- **Records:** stored as JSON with zlib-compressed text, plus indexed columns for filters (status, `escalation.status`, Category, confidence, Answer values). A Document's state and Record are written in one transaction.
- **Inputs:** uploads and URLs are copied, and retry uses the copy. Local paths are referenced, with size and hash recorded; a changed or missing file fails that Document.
- **Retention:** nothing expires automatically.
  - `jobs delete` is refused while the Job runs.
  - `jobs prune --older-than [--keep-records] [--kind ingest]` frees disk; a pruned Job can be exported but not retried.
  - `cache prune` and `cache clear` manage the Judgment cache.
- **Concurrent access:** SQLite runs in WAL mode, and readers open read-only.
- **Network filesystems:** a Workspace on NFS or SMB is refused unless `--allow-network-fs` is given.
- **Upgrades:** older Jobs are always readable and exportable, with storage migrated in place. Resume and retry are refused across a major version.

## 9. HTTP API and CLI

Source: [What API and CLI surface does v0 expose?](https://github.com/Jarrod-Bob/acceleread/issues/9), plus amendments from tickets 10, 17, 23 and 25.

**Inputs.**
- Local paths and globs, multipart uploads, and HTTP(S) URLs. URLs are fetched with a configurable User-Agent, which EDGAR requires.
- Server-side paths only under a configured `allowed_roots`.
- Each Document may carry `external_id` and `user_metadata`.

**HTTP API (`/v1`).**

| Endpoint | Purpose |
|---|---|
| `POST /v1/jobs:validate` | dry-run every submit check; returns warnings, cost and duration estimates |
| `POST /v1/jobs` → `POST /v1/jobs/{id}/documents` (repeatable) → `POST /v1/jobs/{id}/start` | create, fill and queue a Job |
| `POST /v1/documents:ingest` | sync, one Document |
| `GET /v1/jobs` | queue and history (`kind=ingest` hidden by default) |
| `GET /v1/jobs/{id}` | Job summary (§11) |
| `GET /v1/jobs/{id}/events` | SSE, aggregated deltas ≤ 1/s; per-Document events opt-in |
| `GET /v1/jobs/{id}/records` | cursor-paginated; filter by status, `escalation.status`, Category, Answer value; `sort`; `sample=random&n=` |
| `GET /v1/jobs/{id}/records/{doc}` | one Record |
| `GET /v1/jobs/{id}/export` | streamed JSONL, partial while running, `include_text=false` |
| `GET /v1/jobs/{id}/manifest` | the resolved spec |
| `POST /v1/jobs/{id}/cancel` · `/resume` · `/retry` | Job control |
| `PATCH /v1/jobs/{id}` | raise or lower `max_cost_usd` only |
| `DELETE /v1/jobs/{id}` | delete a Job that isn't running |
| `POST /v1/jobs/{id}/records/{doc}/reviews` · `GET /v1/jobs/{id}/reviews` | Reviews (§10) |
| `GET /v1/jobs/{id}/calibration` | suggested `escalate_below` values (§12) |

**CLI** (in-process by default, with `--server URL` to go through an API):

| Group | Commands |
|---|---|
| Running Jobs | `run`, `validate`, `status`, `jobs`, `cancel`, `resume`, `retry --failed` |
| Records and output | `records --flagged`, `export`, `reviews export`, `calibrate` |
| Workspace upkeep | `jobs delete`, `jobs prune`, `cache prune` / `cache clear` |
| Setup | `serve [--no-ui]`, `doctor`, `ocr add-language`, `models fetch` |

`run` writes JSONL to stdout (or `-o`) and progress to stderr. `--no-cache` bypasses the Judgment cache.

**Auth.**
- `serve` binds `127.0.0.1` by default.
- Binding a non-loopback address requires `ACCELEREAD_API_TOKEN`, sent as a bearer token. The UI uses a cookie instead (§10).
- There are no users or accounts.

## 10. Web UI

Sources: [What should the simple UI let a user do?](https://github.com/Jarrod-Bob/acceleread/issues/10), [How is the UI built and served?](https://github.com/Jarrod-Bob/acceleread/issues/16), [ADR 0009](../adr/0009-server-rendered-htmx-ui-on-service-layer.md). Visual reference: the [`prototype/ui`](https://github.com/Jarrod-Bob/acceleread/tree/prototype/ui/prototype/ui) branch, Variant A.

**Stack.**
- Server-rendered FastAPI + Jinja2 + htmx (with its SSE extension), plus a little vanilla JS. There's no Node toolchain or build step.
- Assets are vendored in the wheel, with no CDN. The UI is served at `/` by `acceleread serve`.
- UI routes call the same service layer as `/v1`. **Every UI action has a `/v1` equivalent**, enforced by a test.

**Screens.**
1. **Job console.**
   - Left rail: the FIFO queue.
   - Main area: live progress, cost and the summary counts, with filters above a Records table (server-paginated, 50 rows; a "N new Records" banner instead of auto-refresh).
   - Record drawer: the distribution, Answers with what each read, the escalation reason, and first-pass vs escalated side by side.
   - Job actions: cancel, resume, retry failed, export, manifest (read-only), spend cap.
2. **Needs review mode.** One flagged Record at a time, showing what the Classifier read with unread spans elided. Accept / Correct / Skip, with keyboard shortcuts.
   - **Spot check** sub-mode: random unflagged Records, whose Reviews are tagged `sampled: true`.
3. **Classify now:** a header input for a URL or file, using `documents:ingest`.
4. **New Job form:** attach Set files, add inline Questions as rows, set the Profile, OCR languages, `escalate_below`, LLM escalation and cap, and spend cap, and add Documents. It shows the `jobs:validate` results.
5. **Calibrate panel** in the Job view (§12).

**Review.**
- A Review is a person's verdict on one Judgment: accepted, or corrected to another value. It's allowed on any Classification or Answer.
- Reviews are stored in the Job's Review log, and Records never change. Each Review records the reviewer (`ui` plus an optional free-text name, `cli`, or the token holder), a timestamp, and `sampled`.
- Needs review hides Records whose flagged Judgments are all reviewed.

**Auth.**
- Off-loopback, `/login` exchanges the API token for a signed, HttpOnly, SameSite=Strict cookie.
- State-changing requests also require the `HX-Request` header.

**Styling:** one small classless CSS file, with light and dark following the OS.

## 11. Observability

Source: [What Job-level cost and timing reporting does v0 surface?](https://github.com/Jarrod-Bob/acceleread/issues/23).

**The Job summary** is served by `GET /v1/jobs/{id}`, `acceleread status` and the UI header, and frozen to `summary.json` when the Job ends. It contains:
- **Progress:** Document counts by state, ETA, and throughput (last 5 minutes and overall).
- **Per Classifier:** requests, input and output tokens, cache hits and tokens saved, estimated cost, and effective vs ceiling rate.
- **Extraction:** Pages, Pages OCR'd per engine, worker-seconds, and p50/p95 seconds per Document.
- **Failures by reason,** with up to 3 example Document IDs each.
- **Escalation:** escalated, flagged-over-cap and failed counts, and their cost.
- **Flags:** `stalled`, and the cancel reason (`user | crash_rate | classifier_rejected | spend_cap`).

**Cost.**
- Computed from a versioned price table in the package, overridable in config, and always labelled *estimated*. Cache hits cost $0.
- **Spend cap:** optional `max_cost_usd` per Job. Reaching it auto-cancels with reason `spend_cap`.

**Logs.**
- Stdlib `logging` with a JSON-lines formatter, to stderr and `job.log`, with `--log-level` (default `info`).
- **Never logged:** Document text, Classifier state, Question instructions, keys or the token.
- SDK payload logging is off unless `ACCELEREAD_DEBUG_PAYLOADS=1`, which prints a loud warning.

## 12. Evaluation harness and calibration

Source: [What does the evaluation harness measure, and how is it run?](https://github.com/Jarrod-Bob/acceleread/issues/25).

**Package:** `packages/acceleread-eval`, with the CLI `acceleread-eval run SUITE [--variant …]`. Runs go through the real runner in a scratch Workspace.

**Suites.** A suite is `suite.yaml` (Documents and a Job spec) plus `labels.jsonl` (Categories, Answers, Section boundaries, per-Page OCR truth).
- `corpus-60`.
- `sections-10k`, seeded from EDGAR-CORPUS.
- `ocr-real`: real scans, UK/EU annual reports and non-English filings, assembled during the build.
- `reviews:<job>`.

**Metrics.**
- **Judgments:** accuracy, macro-F1, Brier score, calibration error, and accuracy-vs-coverage over confidence. Broken down per Taxonomy, Question, language and form.
- **Sections:** detection, ±10% boundary agreement, and Verification precision and recall.
- **Extraction:** character error rate, OCR-rule accuracy, Pages/s, peak RSS, and timeouts.
- **Cost and throughput.**

**Running.**
- On demand. CI runs only an offline smoke suite against recorded Jev responses (cassettes).
- Results are committed under `eval/results/`, with a markdown diff against the baseline. Regressions are flagged in the release checklist.

**Variants to run during the build.** Their verdicts become ADR amendments where they change a default.
- An 8k cap vs full text.
- Chunk-and-aggregate.
- Docling vs fast.
- Category shuffling.
- Opus 5.5, Sonnet 5.5 and Haiku 4.5 as escalation models.
- Item-1-only vs head+tail for sector.
- `auto` OCR language.
- Thresholds: the OCR rule, Section Verification, timeouts and memory caps.
- Non-English accuracy.
- Mapping annual-report headings to Section keys.

**`acceleread calibrate JOB --target-accuracy 0.95`** (also in the API and the UI):
- **Suggests** `escalate_below` per Taxonomy and Question from the Review log, with the expected escalation rate and cost. It never changes config.
- Needs at least 50 Reviews per Judgment.
- Weights flagged and sampled Reviews by how they were selected. Without sampled Reviews, it won't suggest a threshold above the flagged range.

## 15. Reconciliations

Several decisions were amended by later tickets. This spec follows the later decision in each case.

| Earlier statement | Now | Where decided |
|---|---|---|
| Token estimate chars/3.5 | chars/3.0 | Classifier seam ticket (8) |
| Docling primary, pypdfium2 + Tesseract as fallback | `fast` (pypdfium2 + Tesseract) is the default; Docling is the opt-in `quality` Profile | Extraction Profile ticket (11), ADR 0005 |
| One Jev request per Document | One request per distinct `reads` group | Questions ticket (15), ADR 0006 |
| Head+tail truncation for all long Documents | Section-aware state for filings; head+tail as the fallback | Questions ticket (15) |
| Judgment cache in the Job's SQLite | Workspace-wide `cache.sqlite` | Storage ticket (17), ADR 0010 |
| `ProcessPoolExecutor` for OCR | Our own worker manager | OCR workers ticket (18), ADR 0002 amended |
| SSE streams per-Document completions | Aggregated deltas ≤ 1/s; per-Document events opt-in | UI build ticket (16) |
| Resume re-queues non-terminal Documents | Resume re-queues `cancelled` and unstarted Documents | OCR workers ticket (18) |
| Manifest fully immutable | Immutable except `max_cost_usd` | Reporting ticket (23) |
| Human review is only a filter, with no workflow | Filter plus a Review log, Spot check and `calibrate` | UI tickets (10), evaluation ticket (25) |
| The OCR rule's English-dictionary check always runs | Skipped unless every configured language has a wordlist | OCR language ticket (21) |
| Section Verification: one Choice per canonical Section | Only for keys some Question reads | Section keys ticket (22) |
| Licence MIT or Apache-2.0 open | Apache-2.0 | Licence ticket (20), ADR 0003 amended |

**Harmonised while writing this spec.** These were not explicitly decided in a ticket, so please confirm them:
1. **`usage` vs `timings`:** the Record schema ticket put `extract_ms` and `classify_ms` in `usage`, and the reporting ticket added `timings`. This spec keeps **counts in `usage`** (`requests, input_tokens, output_tokens, ocr_pages, cache_hits`) and **durations only in `timings`**.
2. **Record `status` vs Document state:** Record `status` is `ok | partial | failed | cancelled`, which adds `cancelled` from the API ticket. The runner's queue states (queued, extracting, `extracted`, classifying) are internal and never appear on a Record.
3. **`needs_review` vs `flagged`:** the Classifier seam ticket used both. This spec uses only `escalation.status = flagged`.
4. **`attempts`:** introduced by the API ticket, now a top-level Record field.
5. **Escalation placement:** `escalation` sits on each Judgment (the Classification and each Answer), not once per Record.
6. **Section `key` → `keys[]`:** needed because a combined heading such as "Items 1 and 2" carries two keys (Section keys ticket, 22).
7. **Taxonomy `reads`:** ADR 0006 has the Taxonomy joining a `reads` group, so the Taxonomy may declare `reads`. With none, it reads the whole Document.
8. **Endpoint and example names chosen here:**
   - `PATCH /v1/jobs/{id}` changes only `max_cost_usd`.
   - `GET /v1/jobs/{id}/calibration` is the `/v1` equivalent of `calibrate`.
   - `examples/edgar-download` is the downloader.

   The tickets decided the behaviour, not these names.
